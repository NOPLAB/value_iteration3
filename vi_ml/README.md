# vi_ml — 価値反復の CNN サロゲート

`vi_lib` の u64 ソルバ（`bench_map`）を教師にして、占有格子＋ゴールから
θ 最小の価値場（秒）を U-Net で回帰し、貪欲降下で経路が出るかを測る。

```
cd vi_ml && uv sync                 # 初回のみ（torch CPU 版）
make ml-data                        # bench_map を build → 64² を 4000 枚、128² を 600 枚解いて out/*.npz
make ml-train                       # U-Net 学習 → out/unet.pt
make ml-eval                        # 値誤差・到達率・経路長比・時間、続けてピラミッド走行
make ml-test
```

| ファイル | 役割 |
|---|---|
| `vi_ml/maps.py` | 地図生成: 部屋＋廊下(BSP) / 迷路 / ブロブ / tb3_house の切り出し。壁は `thicken` で 1 セル膨張（VI は遷移先セルしか見ないので 1 セル壁は 3 セル前進に抜けられる） |
| `vi_ml/vi.py` | PGM+YAML を書いて `bench_map --dump-value` を呼ぶ。セル 0.1 m、safety 0.2 m / 30 s、`frontier2d_sparse` |
| `vi_ml/dataset.py` | 上 2 つを回して `.npz`（free, goal, value, solve_ms, kind） |
| `vi_ml/model.py` | 4ch 入力（free, goal, 境界値, 境界マスク）→ log 正規化した値場の U-Net。境界 ch は窓モード用 |
| `vi_ml/rollout.py` | 半径 3 セル・見通し付きの貪欲降下（真の値場で 100/100 到達） |
| `vi_ml/train.py` | 64² 全体 ＋ 128² から切った 64² 窓（境界 2 セルに真値）を混ぜて学習 |
| `vi_ml/eval.py` | 保留 400 枚で U-Net vs 厳密解 |
| `vi_ml/diffusion.py` | 条件付き拡散モデル（同じ U-Net 本体に x_t と t/T を 2ch 追加、x0 予測、DDIM η=0 で生成）。`make ml-train-ddpm` / `ml-eval-ddpm` |
| `vi_ml/policy.py` | 方策ヘッド: 各セルの最良ジャンプ (dy,dx)∈[-3,3]² を 49 クラス分類。`make ml-train-policy` / `ml-eval-policy` |
| `vi_ml/multiscale.py` | 大きい地図向け（`--mode exact+model/exact/model/flat`）: 粗いレベルを厳密 VI で解き、双一次で拡大した場を誘導チャネルにして小さい U-Net を全面に 1 回かける。`make ml-*-ms` |
| `vi_ml/warmstart.py` | `bench_map --init-value` で CNN の場を初期値にした厳密 VI と cold の比較 |
| `vi_ml/pyramid.py` | 128² を 2× プールした粗場を CNN で出し、ロボット周辺の 64² 窓の境界に流し込んで細場を CNN で出し、8 歩進んで窓を動かす |

## 大きい地図（2026-09-15、Tsudanuma 2944×2000 @0.1 m）

目標は「VI の半分の時間で解ききる」。モデルは 64² 窓で学習した小さい U-Net（4.4M）のまま、全畳み込みなので任意サイズにかけられる。

構成は 2 段 1 パス。粗いレベルは**学習ではなく厳密 VI** で解く（0.4 m セルなら 736×500。前進量をセルサイズに比例させれば「1 手で 3 セル」が保たれる = `bench_map --action-scale`）。それを双一次で拡大して誘導チャネルにし、細かいレベルで小さいモデルを地図全面に 1 回かけて方策を出す。走行は誘導で降りられる間は誘導を降り、誘導の局所最小に落ちたときだけモデルの方策で脱出する。

| 構成 | 解く時間 | 到達率 (20 始点) | 経路長比 |
|---|---|---|---|
| 厳密 VI（0.1 m、基準、16 スレッド） | 18,143 ms | 1.00 | 1.00 |
| 粗い厳密 VI 0.4 m ＋双一次拡大のみ | 1,442 ms | 0.80 | 1.05 |
| **＋学習リファイナ（GPU）** | **3,117 ms** | **0.95** | **1.07** |

VI の 17 % の時間で到達率 0.95、経路は 7 % 長いだけ。内訳は粗い VI 1,389 ms、誘導の符号化 552 ms、モデル 1 パス 1,144 ms。20 走行で局所最小からの脱出が 1,487 回起きている。

保留 40 枚の 256²（`--top 128`）でも同じ効果が出る。

| 構成 | 到達率 | 経路長比 | 時間 | VI |
|---|---|---|---|---|
| 粗い厳密 VI のみ | 0.253 | 1.04 | 189 ms | 283 ms |
| ＋学習リファイナ | 0.762 | 1.16 | 272 ms | 281 ms |

厳密 VI を外して全部モデルに任せると **20 始点すべてで届かない**（再帰 2 段 1,810 ms / 再帰 6 段 1,836 ms / 全面 1 パス 1,446 ms、いずれも到達率 0.00）。
意外なのは失敗した場のほうが数値的にはきれいなことで、モデルのみの場は相対誤差 0.83（誘導は 1.61）、局所最小 1.0 %（誘導は 8.7 %）。
それでも降下はゴールの 68 m 手前（残り 289 秒）で止まる。受容野 64 セルの畳み込みでは 2944 セル先のゴールの順序を作れず、場がほぼ平坦になるため。
測るべきは場の精度ではなく降下がゴールで終わるかどうかで、粗い厳密 VI はその「遠くまでの順序」だけを 1.3 秒で与えている。

効かせるのに必要だったこと。

- **拡大は双一次でなければならない**。最近傍だと 2×2 の平坦部が残り貪欲降下が動けない。256² で真の 2× プール場を降下させると、最近傍 0.14 に対し双一次 0.91。
- **誘導チャネルは絶対値ではなく局所相対値**。学習地図の価値は 400 秒程度までなのに Tsudanuma は 2100 秒まで伸びるので、絶対値のままだとモデルが見たことのない範囲に入り、到達率は 0.80 → 0.10 と**悪化する**。31 セル窓の最小値からの位置を局所レンジで正規化すると、地図の大きさにもセルの時間スケールにも依存しなくなり 0.95 になった。min/max フィルタは分離可能な 1 次元 2 回にする（正方形のままだと campus 地図で 5.8 秒かかる）。
- **走行は誘導優先、モデルは脱出のみ**。粗い場は粗い地図の厳密解なので降りられる限り降りるのが正しく、モデルには粗い地図が表現できない部分だけ任せる。訪問済みセルを拒否するのでループしない。この構成なら原理的に誘導単独を下回らない。
- **粗いレベルのプールは障害物優先**。逆に粗すぎると通路が閉じる（0.8 m で到達セル 3 個）。0.1 m 地図では 0.4 m が分岐点。

学習・評価は Slurm で回す（`vi_ml/slurm/`、`prepare` は 16 シャードの配列ジョブで再開可能）。RTX PRO 6000 で 45,659 窓を 40 エポック 5 分。

## 方策ヘッド（2026-09-13、保留 400 枚・8 始点、GPU 25 エポック、val CE 0.52）

値場ではなく、真の値場に対する貪欲降下（半径 3 セル・見通し付き）が各セルで取るジャンプをラベルにして分類した。走行はロジット順に見通しの通る最初のジャンプを取る。オラクル（真ラベル）の走行は貪欲降下と 400/400 で同一経路。

| kind | n | jump acc | success(policy) | len ratio | policy ms | vi ms |
|---|---|---|---|---|---|---|
| blobs | 94 | 0.592 | 0.992 | 0.99 | 18.6 | 44.9 |
| crop | 78 | 0.761 | 0.997 | 1.00 | 28.5 | 41.1 |
| maze | 72 | 0.900 | 0.852 | 1.00 | 19.5 | 145.6 |
| rooms | 156 | 0.582 | 0.992 | 1.00 | 20.6 | 80.1 |
| all | 400 | 0.677 | 0.968 | 1.00 | 20.9 | 68.2 |

読み方: 値回帰の到達率 48 % が 97 % になり、経路長比は 1.00。迷路も 25 % → 85 %。値に頼らないので局所最小が存在せず、失敗はループ（歩数上限）だけになる。ジャンプ精度 68 % が到達率より低いのは同値のジャンプが複数ある（ラベルはその先頭）ためで、どれを取っても経路は縮む。推論 21 ms は VI の 54 ms より速いが、64² ではまだ差が小さい。

## warm start（2026-09-20、保留 50 枚、frontier2d_sparse、反復上限 2000）

`bench_map --init-value` は θ 最小の 2D 場を全 θ の初期値にする。θ 最小は `min_θ V*(x,y,θ)` なので、
59/60 の θ では真値より低い＝楽観的で、VI は値を上げ直す羽目になる。そこで各初期値には
**その場で任意の向きに回り直すコスト**（180°=9 ステップ ×(1 秒 + そのセルの安全ペナルティ)）を
足した版も測った。これを足せば真値以上になり、`MAX_COST` から下がってくる VI と同じ向きになる。

| init | min(seed−V*) s | iters | updates M | solve ms | max \|Δ\| vs V* (s) | not converged |
|---|---|---|---|---|---|---|
| cold (MAX_COST) | 0.0 | 100 | 3.80 | 90.6 | 0.0000 | 0/50 |
| true θ-min | 0.0 | 98 | 5.64 | 121.3 | 20.1861 | 0/50 |
| true θ-min + turn | 9.0 | 86 | 4.76 | 113.8 | 20.1861 | 0/50 |
| U-Net | -454.6 | 131 | 7.01 | 158.6 | 20.1861 | 8/50 |
| U-Net + turn | -346.7 | 113 | 6.00 | 146.8 | 20.1861 | 8/50 |
| U-Net×1.2 + turn | -270.9 | 104 | 5.75 | 146.9 | 20.1861 | 8/50 |

回転コストを足すと反復回数は 100 → 86 に減るが、更新回数も時間も cold に届かない。理由は
初期値が固定点でない限り**全セルが最低 1 回は動き、その度に先行セルが再評価される**こと。
cold のフロンティアはゴールから広がる波面だけなので、むしろ触るセルが少ない。

反復を k 回で打ち切って貪欲降下の到達率を見る（ms は solve のみ、U-Net 推論 ~20 ms は別）:

| seed | k=0 | k=5 | k=10 | k=20 | k=40 |
|---|---|---|---|---|---|
| cold | 0.025 (0 ms) | 0.207 (12) | 0.393 (16) | 0.693 (24) | 0.955 (45) |
| U-Net | 0.522 (0) | 0.795 (32) | 0.815 (40) | 0.835 (54) | 0.895 (85) |
| U-Net + turn | 0.460 (0) | 0.785 (31) | 0.818 (39) | 0.855 (56) | 0.890 (81) |

数回で 0.52 → 0.80 には上がるが、そこで頭打ちになる（遠くの誤差はゴールからの波が届くまで直らない）。
同じ 45 ms なら cold の k=40 が 0.955、方策ヘッドは 21 ms で 0.968 なので、どちらにも負ける。

**表の `max |Δ| vs V*` 20.1861 は warm start のせいではない。**50 枚中 1 枚（blobs, index 3985）の
2 セルで、`frontier2d_sparse` の cold が本家準拠の `reference`/`frontier2d` と食い違う
（sparse 157.699 s、reference・frontier2d・sparse の warm start はいずれも 137.513 s）。
つまりデータセットの正解側が誤っていて、warm start の結果の方が本家と一致する。
`solvers::conformance` が通る地図では出ないソルバ側のバグで、vi_ml とは別件。（下の節）。

### Tsudanuma でも同じ（2026-09-20、dense frontier2d_sparse、16 スレッド）

`vi_ml.warmstart real` で 2944x2000（0.1 m）を解いた。cold は 8.2 s（compact ソルバの 16-18 s より速い。
dense は状態 353M = 28 GB 要るので、メモリを積める場合の下限）。

| seed | iters | updates M | solve ms | converged |
|---|---|---|---|---|
| cold | 617 | 562 | 8,204 | True |
| 厳密解 + turn | 542 | 4,692 | 24,488 | True |
| 粗い厳密 VI を拡大 + turn | 1,851 | 9,582 | 49,098 | False |
| 粗い厳密 VI を拡大 | 1,851 | 9,944 | 50,657 | False |

理想的な初期値（厳密解そのもの + 回転コスト）でも cold の 3 倍かかる。反復を打ち切る使い方でも、
粗い場からは k=77 で到達率 1.00 になるが 17.7 s で、cold の全解 8.2 s より遅い。

**結論: ML の場を初期値にしても速くならない。**cold の frontier はゴールから広がる波面だけなのに対し、
warm は初期値が固定点でない限り全セルが動き、その先行セルも毎回再評価されるため。
ML の場を活かすなら初期値としてではなく、`exact+model`（粗いレベルだけ厳密 VI、細部はモデル 1 パス、
3.0 s・到達率 0.95）のように**解く状態数を減らす**方向。次の候補は ML の値を下界（ヒューリスティック）に
使って、A* / LPA* のように経路の周りだけ厳密に解く版。

## `frontier2d_sparse` が本家と食い違う（2026-09-20、要調査・vi_ml とは別件）

warm start の検証中に見つけた。保留 60 枚中 4 枚で、`frontier2d_sparse` の解が本家準拠の
`reference`・`frontier2d` と一致しない。index 3985（blobs, 64x64）では:

| solver | 有限値のセル（自由セル 1776） | 値 |
|---|---|---|
| reference（本家） | 1776 | 基準 |
| frontier2d | 1776 | reference と一致 |
| frontier2d_sparse | 1561 | 到達済みセルでも最大 20.186 s 低い |

sparse は 215 セルを未到達のまま止まる。再現用の地図とコマンドは `vi_ml/repro/` に置いた。
`solvers::conformance` が通る地図では出ないので、θ マスク疎評価が依存集合の上位集合になる
という前提が崩れる形状があると思われる。vi_ml のデータセットは sparse で作ったため、
教師ラベルにも同じ誤りが混ざっている（到達率などの指標は cold/warm 両方に同じ基準を使っており、比較自体は有効）。
