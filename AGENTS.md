# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FPGA accelerator for 3D (x, y, theta) Value Iteration path planning, targeting Ultra96-V2 (Zynq UltraScale+ ZU3EG). Goal: solve a 14000×800×60 campus map in <60 s. The same VI algorithm is realized in several coordinated implementations that share a single 16-bit data contract, plus a faithful u64 reference model (`vi_rs/vi_lib`) mirroring the ROS1 original:

- **`vi_fpga/`** — the Vitis HLS kernel (`vi_sweep`), its Linux user-space driver (UIO + u-dma-buf), a C CLI, a host-side reference solver, and the Petalinux/board bring-up. This is the hardware vertical.
- **`vi_matlab/`** — a MATLAB HDL Coder variant of the streaming kernel plus algorithm experiments/benchmarks; mirrors the streaming HLS kernel.
- **`vi_rs/`** — a Rust Cargo workspace: a faithful u64 port of the ROS1 `value_iteration` node (`vi_lib`, which also carries the word-parallel `bitboard` primitives its frontier solvers use, the continuous controllers in `vi_lib::ctrl`, and the VIOLA localizers — the windowed histogram-MCL `GridLocalizer`/`AdaptiveLocalizer` in `vi_lib::localize` and the whole-map histogram `Belief` in `vi_lib::belief`, which coexist; the closed-loop `viola_bench`/`follow_ctrl_bench` bins in `vi_bench` evaluate them). The fast CPU solvers (reference, frontier, block, pyramid, stream-mimic) live in `vi_lib::solvers` — u64, bit-exact with the ROS1 original — and `vi_bench` is the benchmark harness.
- **`vi_rs/vi_planner/`** — a ROS2 (Humble) Rust node (Docker/colcon 資材は同梱の `docker/`): `vi_planner` (**one** node serving both `compute_path_to_pose` and `follow_path` from a **single** value function — replaces planner_server and controller_server together; `follow: false` turns it into a global-only planner to pair with nav2_controller's controller_server). It carries `map_scale` and the out-of-core `frontier2d_sparse_compact` path for maps too large to solve densely, calls `vi_rs` (the u64 `vi_lib` solvers), and builds via colcon in the Docker image.

Phase plan and design specs live in `docs/superpowers/specs/` and `docs/superpowers/plans/` — read them before making non-trivial changes to algorithms, datatypes, or memory layout. Specs are written in Japanese.

## Repository layout (important)

The C/HLS/driver/Petalinux code lives **under `vi_fpga/`**, not at the repo root. The root `Makefile` is a thin wrapper that delegates the software/FPGA/EDF targets into `vi_fpga/...` (and `matlab-*` / `rs-*` / `ros2-*` into their own trees), so the commands below are run from the repo root. Note: recursive `$(MAKE)` invocation fails under Windows GnuWin32 (`e=87`); run these on Linux/WSL (which is also where the Ultra96-targeted builds belong), or invoke the sub-Makefile directly (`make -C vi_fpga/host test-host`).

## Build & Test

### Software (driver + host CLI), under `vi_fpga/`

- `make driver` — build `libvi_sweep.a` / `.so` (UIO + u-dma-buf Linux ops + mock) via `vi_fpga/driver/uio/`.
- `make host` — build `vi_fpga/host/vi_cli` linked against the Linux libvi_sweep (depends on `driver`).
- `make test-host` — build the mock-only lib and run all host unit tests (`vi_fpga/host/test/test_*.c`). No FPGA needed.
- `make test-hw` — HW integration via SSH. Requires `VI_TARGET_HOST=<ultra96-hostname>`; runs `vi_fpga/host/test/hw/run_smoke.sh` then `run_big.sh`, which scp the CLI + generated maps to the target and execute `vi_cli --verify` there.
- Run a single host test: `make -C vi_fpga/host test/test_penalty.run` (pattern: `test/<name>.run`).
- Host-only CLI with the mock backend (no UIO needed, useful for local debugging): `make -C vi_fpga/host cli-mock` → `vi_fpga/host/vi_cli_mock`.

### FPGA build (`vi_fpga/Makefile`)

Tools must be on `PATH` — invoke bare `vitis-run` / `vivado` (Vitis 2025.2). Do **not** prefix with `source settings.sh`. Tile and streaming kernels have fully separate build paths. All TCL scripts live in `vi_fpga/tcl/`; build artifacts go to `vi_fpga/build/`. Select the kernel with `KERNEL=tile` / `KERNEL=stream` (default `tile`), both from the root wrapper and when invoking `vi_fpga/Makefile` directly (`make -C vi_fpga csim KERNEL=stream`).

- `make csim KERNEL=stream` — HLS C-simulation of streaming kernel (`vi_fpga/hls/stream/`); `KERNEL=tile` for the tile kernel (`vi_fpga/hls/tile/`).
- `make hls KERNEL=tile` — HLS synth + IP export (tile) into `vi_fpga/build/hls_build_tile/`, IP to `ip_repo_tile/`; `KERNEL=stream` for streaming.
- `make bitstream KERNEL=tile` — HLS + Vivado synthesis + bitstream for tile kernel, project `vi_fpga/build/vi_tile/`; `KERNEL=stream` → `vi_fpga/build/vi_stream/`.
- `make clean-fpga` — clean all FPGA build artifacts (`make -C vi_fpga clean`; clean one kernel with `make -C vi_fpga clean_hls KERNEL=<k>` / `clean_vivado KERNEL=<k>`).
- Register offsets live in the hand-maintained `vi_fpga/driver/uio/vi_regs.h` (shared by the Linux and mock backends); after changing the HLS kernel interface, diff them against the HLS-generated `xvi_sweep_hw.h` in the HLS build output.

### Rust workspace (`vi_rs/`)

A 2-crate Cargo workspace (`vi_lib`, `vi_bench`). `vi_rs/vi_planner` (the ROS2 node) also lives in this directory but is **not** a workspace member — see the ROS2 section. The former `vi_core` (16-bit type-width record, referent-less), `vi_algorithm` (its `bitboard` primitives are now `vi_lib::bitboard`) and `vi_fixtures` (orphaned synthetic u16 maps) crates were removed in the dependency-trimming passes. Driven from the repo-root Makefile (these targets are current):

- `make rs-test` — `cd vi_rs && cargo test --workspace`.
- `make rs-bench` — criterion microbenchmarks (`cargo bench -p vi_bench`) over the u64 `vi_lib` solvers (the `bitboard` microbench exercises `vi_lib::bitboard`).
- `make rs-bench-summary` — `bench_summary` CLI: a `benchmark_vi.m`-compatible macro comparison table across sizes/map-types over every u64 solver, emits CSV/markdown. Each solver is bit-exact with the ROS1 original (mismatch=0 vs the Reference oracle).
- Run a single crate's tests: `cd vi_rs && cargo test -p vi_lib`.
- On this WSL host, run cargo from **outside** the repo with `--manifest-path` (the repo `.cargo/config.toml` ROS patches break a plain in-repo cargo run).

The u64 solvers in `vi_lib` are the bit-exact regression oracle. The default solvers (Reference/Frontier/Block/Pyramid/Stream, exercised by `rs-bench`/`rs-bench-summary`) are serial; a deterministic multithreaded CPU path also exists in the `frontier2d_par*` family — `std::thread`-based, **not** rayon — and is exercised via `bench_map`.

The node publishes its estimate on `viola_pose` (PoseStamped, per scan correction) and, with `publish_tf: true` (default false), the AMCL-contract `map→odom` TF (needs `odom_topic`; stamps future-dated by `transform_tolerance` — never combine with an external localizer that also publishes map→odom).

One package:

- `vi_planner/` — **the unified planner: one node, one value function, both Nav2 actions.** (The former `vi_interfaces`/`vi_node` — the ROS1-interface-equivalent Vi.action server — and `vi_global_planner` — the global-only planner — were removed in the 2026-08 trimming pass; `follow: false` below covers vi_global_planner's role, and the house-oracle comparison runs ROS-free via `vi_u64_bench`.) **`vi_planner` sits under `vi_rs/` but is deliberately outside the `vi_rs` Cargo workspace** (its `Cargo.toml` has an explicit empty `[workspace]`, and it is not in the workspace `members`) so its `path = "../vi_lib"` dep doesn't pull it into that workspace. `rclrs`/`nav_msgs`/`nav2_msgs` are wired as `*` deps and `[patch.crates-io]`-redirected (generated `.cargo/config.toml`) to colcon-built crates; the **binary links only via colcon** (`make ros2-build`), not plain `cargo build`. Serves `compute_path_to_pose` *and* `follow_path`, replacing planner_server and controller_server simultaneously (same crate isolation pattern). This is the successor to the old `vi_global_planner` + `vi_local_planner` **pair**, which ran in two processes and therefore solved the *same* value function for the *same* goal twice — doubling both time-to-first-motion and resident memory — while the `nav_msgs/Path` the global side produced was discarded by the local side except for its final pose. Here a goal is solved once (`PlannerCore::prepare_goal_with_progress`), `compute_path_to_pose` is a greedy rollout of that solved field (`rollout_path_on` + `densify` — exactly the old cache-hit path), and `follow_path` refines the *same* field inside the ±1m window: move window → inject `local_penalty` from `scan_topic` LaserScans → re-iterate under `refine_budget_ms` → greedy action to `cmd_vel` (delta_fw [m] → linear.x, delta_rot [deg] → angular.z, 本家 `ViNode::decision` 準拠; remap to `cmd_vel_nav` in a Nav2 bringup). Goal detection is the VI `final_state` itself; a policy-less pose borrows the nearest neighbor's action within a fixed 0.2 m. **Lock discipline matters**: the two actions share one `Mutex<PlannerCore>`, so the follow loop takes the lock *per tick* (10 Hz, 40 ms budget) rather than for the whole follow — otherwise the BT's 1 Hz replan would block until the goal is reached. The follow loop also re-checks `is_cached_goal` every tick, so if a plan request for a different goal replaces the cache it preempts instead of driving on a stale policy. RViz: `value_function` (θ=0 slice, solve progress every `value_publish_interval_ms` + once on convergence) and `local_window_value` (the clamped ±1m window at the robot's current-heading θ slice). There is no `local_value_function` topic — there is only one value function now. A third grid, `belief`, carries the localizer's belief (θ-marginalised, drawn by `vi_lib::belief::mass_to_grid` on the same 0..98 relative scale, zero mass = 0 so RViz's costmap palette leaves it transparent — `-1` there is an opaque grey that would veil the map); it is published from the seed and scan callbacks under the same `value_publish_interval_ms` throttle, is empty for `localizer: external`, and covers the whole map for `belief`/`viterbi` but only the current window (and, for `adaptive`, the current level's resolution) for the windowed estimators. Supports `map_scale`/`downsample_policy` and the out-of-core `frontier2d_sparse_compact` solver (`compact_sink_dir`, which when unset spills the sink to `/tmp/vi_planner_sink` once it exceeds `compact_ram_limit_mb` — 0, the default, meaning half of `MemAvailable` — the follow loop re-reads the sink on every patch recenter; the mmap sink is `vi_lib::solvers::frontier2d_sparse_compact::MmapSink`, shared with `bench_map`). The follow loop needs a dense `ValueIterator::states`, which a compact solve never allocates, so with the compact solver it hydrates a **patch** around the robot instead of the whole map: `±1m window + transition reach + slack` cells (27×27×60 ≈ 2.5 MB at 0.25 m/cell), filled from the sink (values/policy) and the static grid (`free`/`penalty`, evaluated in *global* coordinates so `State::from_occupancy`'s row-crossing bug matches what the solve saw). Everything outside the window stays frozen at the compact values and serves as the boundary condition; the invariant "the window's transitions land inside the patch" is checked at startup against the measured transition table (`transition_reach`), and the patch is re-centered when the robot nears its edge. Two deliberate differences from the dense path: `compute_path_to_pose` rolls out over the pristine sink (so scan penalties do not reach the published path — following still avoids obstacles via the patch), and re-centering discards that tick's local refinement (the next scan restores it). **Local → global feedback (`global_sweep`, on by default, dense and compact alike):** because both actions read the same `states`, what the follow loop learns from the laser *is* in the global field — but `refine_pass_until` only sweeps the ±1m window, so the raised values never propagate and a rollout descending from 20 m away keeps aiming into a blocked corridor (this is the entry point for `LoopDetected` and the BT's recovery loop). `PlannerCore::sweep_global` closes it with an **active set** over the shared field, reusing `value_iteration_at` so local/global/solve stay on one update rule (no new Bellman code). A cell's value can only move if a transition target's value or penalty moved, so it sweeps the cells that changed, dilated by the measured transition reach (`vi_lib::bitboard::Bitboard2D`), and stops when nothing moves — an empty frontier *is* the fixed point. Work is therefore proportional to what actually changed, not to the map: measured ~11–14 cell-visits per cell whose value moved, **flat across map sizes** (the earlier implementation swept the whole `states` array, ~72 full passes to Δ=0, and needed `sweep_orders`, which this node no longer reads — vi_lib still allocates them, so the 80 B/state figure below is unchanged). It is chunked and must **not** run a whole propagation under the lock — the 10 Hz follow loop `try_lock`s the same mutex and stops the robot after 3 consecutive misses; `global_sweep_duty` (default 25 %) is the CPU share. Seeds go in at exactly two places: the ±1m window rect whenever `refine_for` moves a value (the whole rect, not just the moved cells, so the dilation also catches predecessors *outside* the window whose successor's penalty changed), and the whole map on an `early_start` handover. The `dirty` flag still gates whether the thread runs at all; it clears when the frontier empties. **`done` now means "converged", not "one pass finished"** — with `value_publish_interval_ms: 0` the global RViz slice therefore updates only when the field settles, which while driving along a wall may be never (keep the 500 ms default). The fixed point is unique only up to ~1 LSB (the update truncates with `>> PROB_BASE_BIT`), so a field descended from `MAX_COST` and one ascended from a perturbed field can differ by 1–2 units out of 3e9 — but *visit order* does not matter: `vi_lib`'s `conformance_resweep_propagates_a_raised_penalty` gates every solver's re-sweep against the whole-sweep oracle bit-exactly, and the planner's own corridor scenario matched the old whole-map sweep on all 245,760 states. Under compact there is no whole-map `states`, so the same feedback runs as **tile repair on the sink** (`cb4e9e6`, 2026-08-04): one tile is a 16-cell interior plus a halo of the measured transition reach, hydrated from the sink, swept with the halo frozen, changed columns written back, and every tile within reach of the change re-queued; an empty queue is convergence. Being block Gauss–Seidel it settles on the **same fixed point** as the dense propagation (a synthetic test pins the values outside the window to the dense result) — it is the same active-set idea at tile granularity rather than cell granularity — and the work is proportional to how far the change propagates rather than to the map size — resident memory is one tile (~1.9 MB at 0.25 m/cell). What makes the sink a shared field at all is `commit_window` writing the moved window back every tick (`20a25e4`) plus a 1 B/cell `PenaltyOverlay` that keeps the `local_penalty` backing those values. The guard that used to refuse compact + `global_sweep` is gone from both this node and the daifuku launch. `local_penalty` outside the window is never cleared (本家 `ViNode` behaviour, deliberately kept) — a penalty injected while passing an obstacle distorts the global field for the rest of that goal. Dense costs 80 B/state (`states` 56 + `sweep_orders` 24; measured 654.8 MB for 19F at map_scale 2) and startup refuses rather than being OOM-killed when that exceeds the machine's `MemAvailable` (warning past half of it) — there is no `dense_limit_mb` knob, the answer is what the machine actually has. **Waypoint prefetch (`waypoint_prefetch`, off by default):** `nav2_waypoint_follower` drives a tour one `navigate_to_pose` at a time, so every waypoint change runs a whole fresh solve with the robot standing still (29 s measured for 19F, 87 s for tsudanuma under compact). With the flag on, the node subscribes to an ordered `nav_msgs/Path` on `waypoint_topic` (latched; `daifuku_waypoint_manager`'s panel publishes it on `/waypoints`), and whenever a goal is established it looks that goal up in the list and hands the *successor* to a `Prefetcher` — a second solve-only `PlannerCore` on its own thread. `prepare_goal_with_progress` then checks the prefetcher before solving: ready → adopt the field wholesale (`SolveStats::adopted`, zero iterations), still in flight for the same goal → wait for it (never slower than solving inline), a different goal → cancel it and solve normally. **The worker never takes the shared `Mutex<PlannerCore>`** — it owns its own core and hands over only the finished field, because holding that lock would stop the robot through the same `try_lock` path the sweep thread is rationed for. Consequences to keep in mind: exactly two value functions are live at once (every path frees the old field before allocating the new one, so it never becomes three), so dense doubles RAM and compact doubles the sink on disk — the memory check is against the doubled figure; the prefetched field is solved from the **static map only** (driving-time `local_penalty` is not carried across, same as any re-solve); `waypoint_prefetch_threads` (default 1) rations the solve, but only on the compact path, since `frontier2d_sparse` reads the process-wide `VI_THREADS`. The compact sink then **must** use one throwaway directory per solve (`PlanConfig::compact_sink_gen` → `<compact_sink_dir>/gen<N>`, removed when the field drops): the filenames inside a sink dir are fixed and `MmapSink::new` truncates, so two live fields sharing a directory means the second solve silently zeroes (or SIGBUSes) the field the robot is driving on. **Early start (`early_start`, off by default):** the same standing-still problem attacked from the other side — rather than moving the solve earlier, start driving *before* it finishes. Driving off only needs a policy from the robot's current pose to the goal, not one for the whole map, so with the flag on `prepare_goal_with_progress` returns as soon as one exists — **it does not abandon the solve**, the rest of the field is finished in the background while the robot drives. The test is the rollout itself (`core::reaches_goal` — the very `rollout_path_on` that `compute_path_to_pose` returns), evaluated at each `solve_chunk` boundary on the dense path and after each band finalize on the compact path (via the observer's `Stop` in `solve_compact_mapped_observed`; the non-observed `solve_compact_mapped` is a thin delegate to it). Deliberately not an approximate "has the value reached the robot yet" proxy: those fail by leaving one cell of the path unfinalized, i.e. a `plan` that fails on a field the node just declared good enough. The field handed over at that moment is sound on both paths, for different reasons. Compact finalizes in ascending value order (a finalized column is at v\* and immutable), so what is in the sink is **bit-identical to the fully solved field** — unfinalized columns just read `(MAX_COST, -1)` — and "a path exists" therefore means every column along it is exact. Dense values descend monotonically from `MAX_COST`, so a mid-solve field always satisfies V ≥ TV: greedy descent strictly decreases V and cannot cycle, but the path is *not* necessarily optimal. Either way `global_sweep` finishes the field off while the robot drives — same Bellman update as the solve (`value_iteration_at`), so it settles on the same fixed point — and the field is then marked complete: dense clears `partial` when its active set empties (nothing moved anywhere ⇒ V = TV ⇒ V\*), compact when the repair queue empties (block Gauss–Seidel, same fixed point). Two tests pin that the finished field is **bit-exact with the fully solved one**, one per path. Only the trigger differs, because tile repair propagates outward *from a change* rather than from a flag: **both** now need the whole map pushed in as a starting point — dense via `seed_sweep_all`, compact via `Repair::enqueue_all` (a finalized tile/cell costs one Δ=0 pass), which is what makes the completion independent of where the robot happens to drive. Because the background solve is what finishes the field, `early_start` **turns `global_sweep` on** if it was off (logged, not silently). A test drives 2000 ticks across a mid-solve sink to the goal. The anchor is an explicit argument (`prepare_goal_with_progress(goal, from, …)`), never stored state, and `from: None` makes the call run to convergence — which is why the prefetch worker, which goes through `prepare_goal`, always solves to convergence (its anchor would be where the robot is now, not where it will be when that goal activates). Two costs. Until the background solve catches up, everything off the path is unsolved, so if the robot leaves the path the field can fail to yield an action; the escape is `discard_partial` — `plan_with_progress` drops the field and re-solves inline when the rollout fails, and the follow loop drops it before aborting on the no-action timeout. Without that escape the failure is permanent, since the BT's 1 Hz replan is a cache hit and never re-enters the solve. And on compact the cut has band granularity: finalization advances by `COUPLE_SAFETY(4) · transition reach · max penalty` (≈500 steps ≈ 150 m of travel at 0.1 m/cell with `safety_radius_penalty: 30`), so a map whose entire value range fits in one band converges in two waves and never starts early — **silently, with no warning**. Single-building maps are in that class; a coarser `map_scale` narrows the band, so wide maps benefit most. Whether it fired is `SolveStats::partial` (logged as "enough to start driving" / ", still solving"), and the field announces itself again once the background solve has converged. Orthogonal to `waypoint_prefetch`; the two combine. **VIOLA — localization inside the planner (`localizer`, default `external`):** anything other than `external` makes the node its own localizer instead of consuming `pose_topic`, which then becomes a **manual seed** (remap it to `initialpose`, never to an MCL's continuous output — every message re-seeds). Two families coexist, and they are different estimators, not two settings of one. **Windowed** (`vi_lib::localize`, the `Localizer` trait): `grid` is a histogram MCL on a `belief_radius` window at *native* resolution; `adaptive` adds the multi-resolution level cascade (expand to a coarse whole-map level when the observation stops matching = EMCL's expansion resetting, contract back on re-lock), which is what recovers from kidnapping and starts up unseeded; `adaptive_viterbi` runs that same cascade's global level under min-plus (MAP). Of the windowed family only `adaptive` proposes `reloc_targets` (`grid` has no lost state to propose from). **Whole-map** (`vi_lib::belief::Belief`): `belief` (sum-product) or `viterbi` (the same field under min-plus/MAP) puts the belief on **the same grid the ValueIterator gets** (post-`map_scale`) with the likelihood field built at native resolution — no window to recenter and no level machinery, so `belief_radius` does not apply. Recovery there is one mechanism instead of a cascade: `BeliefConfig::reset_quality` (0.25, fixed in vi_lib) mixes free-uniform into the field when the observation stops matching, and lost is a **latch** (`lost_ess`, 500) rather than an instantaneous predicate — a kidnapped belief is confidently *wrong*, so its ESS stays small, and the reset rewrites the quality EWMA inside the same `observe`, erasing the evidence before anything outside can read it. `viterbi` costs ~183 ms per `observe` on tb3_world (min-plus sweeps the whole grid; sum-product walks only the active set), i.e. over the 40 ms follow budget — treat it as a `viola_bench` knob, not a runtime mode. Whichever family is selected, the estimator lives in the node behind its own mutex (`node::handles::Loc`), deliberately **not** inside `PlannerCore`: a solve holds the core lock for up to ~30 s, and the scan callback must keep correcting through it (lock order is always localizer → core, never nested the other way). `qmdp` (off by default) switches multi-modal ticks to `argmin_a Σᵢ wᵢ·Q(sᵢ,a)` over the belief's top cells; unimodal ticks stay on `follow_controller`. **Multi-modality is counted in *peaks*, not cells** (`vi_lib::belief::mode_count`, top cells thinned by `QMDP_MIN_SEP_M` = 0.5 m): a whole-map belief keeps thousands of non-zero cells even when converged, so a `top_cells(k).len() >= 2` test is always true there and `qmdp: true` would put QMDP on *every* tick, so `follow_controller` never runs and the coarse 6-action argmin cannot finish the approach. Measured on the tb3 demo: cell-counting stalls 0.29 m short of the goal for 302 s; peak-counting reaches it in 19 s. (The windowed estimators prune hard enough that cell-counting happened to work, which is why the bug only appeared with the whole-map field.) **Margin inflation under localization uncertainty (`sigma_margin_gain`, 0 = off):** Ueda et al. 2023 (§4·2·2) widen the wall margin `m` by the localization spread σ, which in that paper costs a fourth state dimension (the `BeliefModel` this repo tried and dropped in `0cae528`). The same field shape comes out of the ±1m window instead: `PlannerCore::inflate_by_sigma` → `ValueIteratorLocal::inflate_by_sigma` writes a `local_penalty` band of the *same* strength as the static margin into the window cells whose L∞ distance to a **map** obstacle falls just outside `safety_radius`, out to `σ · sigma_margin_gain` (clamped to the window radius — a window that becomes one solid band leaves the robot no exit). L∞ because `State::from_occupancy`'s static margin is a square range, so `d <= margin` means exactly "already inside the static band"; the distance field is built once, lazily, from `states`' `free` flags. Inflating from map obstacles rather than scan hits is the whole point — the paper's target is obstacles the laser cannot see. σ is `vi_lib::belief::spread_m`, the weighted RMS radius of the localizer's top cells (both estimator families expose `top_cells`), deliberately *not* the paper's `∛(σx·σy·σθ)`: discrete hypotheses often line up on one axis, and the geometric mean collapses to 0 there even when the belief is 2 m wide. The band follows `local_penalty` lifetime rules (never cleared outside the window, gone when the goal is re-solved) and reacts to the *current* σ only — reasoning about σ two steps ahead is what the 4-D formulation buys and this does not. `viola_bench` reports the wall clearance the robot actually kept (`clr_min_m`/`clr_avg_m`, off the same `chamfer_dist` the start picker uses; measured on tb3_house, `dead` reckoning collides at min 0.15 m while the localized runs hold 0.90 m), but it drives the `ValueIterator` directly and never goes through `PlannerCore` — it measures localizers, not this flag, which needs the demo or a real run. **Active relocalization (`active_reloc`, off by default, given up after 30 s):** while lost, instead of waiting stopped for passive recovery, `PlannerCore::prepare_reloc_goal` solves a **multi-goal** VI whose `final_state`s are the hypothesis-disambiguating points (`Localizer::reloc_targets` → `ValueIterator::set_goal_region`) and drives it under QMDP, so whichever hypothesis is true the robot moves toward the place that tells them apart. On re-lock the follow loop re-solves the real goal (the reloc cache deliberately does not match it, so no special teardown is needed). Startup refuses it unless the localizer has a multi-modal belief to disambiguate — `adaptive`, `belief` or `viterbi` (`grid` never declares itself lost, `external` has no belief) — and a dense solver, the compact sink solver being single-goal. The displacement search itself is one shared function (`vi_lib::belief::reloc_targets`): both families feed it their top modes plus a free/likelihood accessor pair, since their likelihood fields are separate types. Only the *peak selection* differs, and it has to: a whole-map belief spends thousands of cells on a single peak, so `Belief::reloc_targets` thins every cell above 5 % of the max weight (`belief::modes`, 1 m separation) instead of thinning a fixed top-k the way the windowed levels can. **Parameter surface**: the node declares 58 startup parameters. Anything with a single correct value (sweep chunk width, compact patch slack, the invalid-range sentinel, MPPI temperature, the retry settle …) is a `const` at its use site — `node::boot`, `node::sweep`, `node::follow_loop`, `node::msg` — not a knob; promoting one back is moving it into `node::params`. Limits that depend on the machine default to `/proc/meminfo` rather than to an invented MB number: the dense field size has no knob at all (over `MemAvailable` refuses, over half warns), while the compact RAM sink keeps `compact_ram_limit_mb` — 0 means half of `MemAvailable`, and it stays settable because whether the sink belongs in RAM depends on what else runs on the box. The rclrs-free core (`src/core/`: `mod.rs` = the public types, `PlannerCore` and the dense path; `compact.rs` = the out-of-core machinery only — sink, follow patch, `PenaltyOverlay`, tile `Repair`, and the `PlannerCore` methods that only run there; `prefetch.rs` = the waypoint prefetch worker; `tests.rs` = all of it, one module) is host-testable. **Standalone (`standalone`, off by default):** the node additionally serves `navigate_to_pose` and `follow_waypoints`, replacing `bt_navigator`, `behavior_server`, `waypoint_follower` and `smoother_server` — a Nav2 robot can then run with *no* Nav2 navigation node at all (map_server and the localization stack are unaffected). The action types stay `nav2_msgs`, so RViz and existing clients need no rewiring. **Never set it in a params file** — with the Nav2 BT also up, `navigate_to_pose` would have two servers and a client binds to whichever it discovers first, silently. Four Nav2-imposed limits go away, and each of them is a thing VI was losing rather than a convenience: the BT's 1 Hz `ComputePathToPose` (a rollout + densify *under the shared mutex*, competing with the 10 Hz follow loop every second) becomes one rollout per goal, published to `plan` for display only; a failed rollout no longer kills the goal (`LoopDetected` means greedy descent oscillated, not that there is no policy — following draws one action at a time and often works anyway); retries become `run_goal`, which between attempts runs `run_settle` — a wait that keeps calling `observe_scan`/`refine_for`, i.e. the *only* path by which `set_local_cost`'s penalty halving undoes a stale "impassable", which the BT's `Wait` could not do because `follow_path` was not running (its `Spin`/`BackUp` could not run at all, wanting a `local_costmap/costmap_raw` no VI wiring publishes); and `follow_waypoints` hands the tour straight to the `Prefetcher`, closing the hole where `waypoint_prefetch` silently did nothing unless something happened to publish `waypoint_topic`. Params: `goal_retry_limit` (3, negative = unlimited), `stop_on_failure` (false), `waypoint_pause_sec` (0.2 — also a settle, not a sleep); the between-retry settle itself is a fixed 3.0 s (`boot::GOAL_RETRY_SETTLE_SEC`). All four follow-driving servers share one preempt slot, so a new goal of any kind stops the running one. Launch: `launch/vi_planner.launch.py` (node only) and `launch/navigation_launch.py` — a robot-agnostic derivative of nav2_bringup's `navigation_launch.py` that brings up the full Nav2 navigation stack with vi_planner in place of planner_server (moved here from the removed vi_global_planner; **daifuku_autonomous includes it from the vi_global_planner package path — update that include**); daifuku_autonomous drives the standalone mode from `navigation.launch.py`'s `nav2:=auto|true|false`.
- The follow side is selected by `local_planner` in `vi_planner/launch/navigation_launch.py`: `local_planner:=vi` (default) = `vi_planner` alone (both actions); `local_planner:=nav2` = `vi_planner` with `follow: false` (compute_path_to_pose only) + nav2_controller's controller_server. `follow: false` never starts the follow_path server, so the two wirings cannot collide.
- The rclrs-free library (vi_planner: `core`) runs via `cargo test --lib` **inside the Docker image**; on the host it is checkable via a scratch isolation crate that `#[path]`-includes those modules (the repo `.cargo/config.toml` ROS patches block a plain host build). A plain `cargo test --test ...` does NOT work — it forces cargo to build the rclrs binary, which only links under colcon (so those tests live in the library, not `tests/`). The shared ROS-view conversions live in `vi_lib::bridge`.
- `nav2_msgs` Rust bindings are produced in the **Docker image's** `/ros2_rust_ws`: the Dockerfile clones `navigation2` (humble) and colcon-builds `nav2_msgs` there after rclrs, so `rosidl_generator_rs` emits the Rust crate that the generated cargo config patches in (requires `ros-humble-nav2-common`, installed in the image).

See `docs/superpowers/specs/2026-05-29-vi-ros2-design.md` for the original ROS2 design (its `vi_node` Vi.action server has since been removed).

## Architecture

The HLS hardware vertical (`vi_fpga/`) has four integrated layers sharing the same 16-bit data contract defined in `vi_fpga/hls/common/vi_hls_common.h` (shared types, sentinels, `cost_of`, `load_transitions`; `vi_types.h` / `vi_stream_types.h` hold only kernel-specific constants). The MATLAB (`vi_matlab/`) port replicates that same contract; on the Rust side the algorithm constants live in `vi_bench::params` as benchmark values (the u64 model in `vi_lib` has its own faithful-port logic). Keep them all in sync.

Datatypes: `value_t`/`penalty_t` are `ap_uint<16>`; offsets `ap_int<8>`. Sentinels: `PENALTY_OBSTACLE = 0xFFFF` (impassable); `PENALTY_GOAL = 0xFFFE` — **when read as a neighbor's penalty it must be treated as 0** so the goal cell's value stays pinned at 0 (this convention is load-bearing; the single C-side definition of the per-cell update is `vi_fpga/driver/uio/vi_bellman_cell.h`, shared by the host reference, the mock device, and the HLS testbench reference (`vi_fpga/hls/common/vi_reference.{h,cpp}` includes it and `host/src/transitions.c` directly). The Rust u64 model in `vi_lib` pins goal cells its own way in `value_iterator.rs` (`set_goal` / `set_state_values`)). Transition table is a packed `(dix, diy, dit)` word per `(action, theta)` — 6×60 = 360 entries, precomputed on ARM and DMA'd into the kernel.

### 1. HLS kernel (`vi_fpga/hls/tile/` and `vi_fpga/hls/stream/`)
Two kernel architectures share the data contract but differ in how they sweep the grid:

- **Tile kernel** (`vi_fpga/hls/tile/`): Dataflow pipeline `vi_sweep_top` = `load_tiles` → `compute_bellman` → `store_tiles`, processing 32×32 tiles with a 6-cell halo (TILE_W_H = 44). Two CUs are instantiated in the Vivado BD for red/black tile sweeping.
- **Streaming kernel** (`vi_fpga/hls/stream/`): Strip-based row streaming via `vi_sweep_stream`. Processes horizontal strips using 13-row line buffers (`WINDOW_ROWS = 2*HALO_MAX+1`). Pipeline: `load_store_row` feeds rows → `stream_strip` manages the line buffer → `compute_row` does per-cell Bellman updates. Two CUs split the map vertically.

### 2. Device layer (`vi_fpga/driver/uio/`)
`vi_device.h` defines a `vi_device_ops_t` vtable (init/shutdown/read_reg/write_reg/wait_irq/map_buf) with two implementations:
- `vi_device_linux.c` — real UIO + u-dma-buf (requires the device-tree overlay in `vi_fpga/petalinux/meta-vi-sweep/recipes-bsp/device-tree/files/vi_sweep.dtsi` applied via Petalinux on the target).
- `vi_device_mock.c` — in-memory software model used for host unit tests and `cli-mock`.

`libvi_sweep.c` sits on top of the vtable and exposes the public API (`libvi_sweep.h`). Build flavors:
- `libvi_sweep.a` / `.so` — full build, both backends.
- `libvi_sweep_mock.a` — built with `-DVI_MOCK_ONLY`, no Linux ops; used by `test-host` and `cli-mock`. Any code touching `vi_linux_ops` must be guarded by `#ifndef VI_MOCK_ONLY`.

Register offsets live in `vi_fpga/driver/uio/vi_regs.h`, shared by `libvi_sweep.c` and the mock device; check them against the HLS-generated `xvi_sweep_hw.h` (in the HLS build output) after changing the kernel interface.

### 3. Host CLI + reference (`vi_fpga/host/`)
`vi_cli.c` loads a PGM map + YAML metadata (`map_pgm.c`), builds the penalty field (`penalty.c`), computes the transition table (`transitions.c`), opens the vi_sweep device, runs sweeps, and optionally verifies against `vi_reference_c.c` (pure-C value iteration matching the HLS testbench reference; the per-cell Bellman update itself is the shared `driver/uio/vi_bellman_cell.h`, which the mock device also calls). `--verify` asserts bit-exact equality vs the reference; this is the oracle for HW correctness. Unit tests in `vi_fpga/host/test/` exercise each module and a full mock-backed run (`test_vi_run_mock.c`, `test_reference_eq.c`).

### 4. FPGA/board bring-up (`vi_fpga/tcl/`, `vi_fpga/vivado/`)
`create_bd_*.tcl` / `create_project_*.tcl` (in `vi_fpga/tcl/`) build the Vivado block design wrapping two `vi_sweep` CUs with AXI and interrupts. The HLS csim/export entry tcls are 3-line stubs over `vi_fpga/tcl/hls_common.tcl` (set `kernel`/`mode`, then source it).

### 5. Rust algorithm port (`vi_rs/`)
- `vi_lib` — a faithful u64 port of the ROS1 `value_iteration` node (`ValueIterator` / `State` / `Action`, PROB_BASE = 2^18 fixed point), reproducing its quirks (including the original's int-division and margin-penalty bugs). `solvers::solve(&mut ValueIterator, U64Solver, max_iter)` dispatches 13 `U64Solver` variants; `solve_observed(.., &mut dyn SolveObserver)` is the observed form — every solver calls `SolveObserver::boundary` at its natural granularity (round / sweep / block pass / band finalize / a documented pop count), where the caller can cancel (preempt), read the mid-solve field via a lazily-materializing `SolveProbe` (`policy()` → `&dyn PolicyView`), or stop early (early_start); `U64Solver::caps()` declares per-variant capabilities (`exact`, `partial` = UpperBound/ExactPrefix, `out_of_core`, `parallel`, `resweep`), and `solvers::conformance` gates **all** variants on convergence, caps-driven correctness, boundary invariants, prompt cancel, stop-then-rollout soundness, and re-sweep. **`resweep`** is the one capability that is not about solving from scratch: it says the solver can be handed an already-converged field with `local_penalty` added and drive it to the whole-sweep fixed point. Solving from `MAX_COST` only ever *lowers* values, so every frontier solver used to propagate on `value < before`; a penalty injected while driving *raises* them, and that predicate then emptied the active set on round 1 and silently left the far field stale. Fixed to "the value moved" in frontier2d/3d/stack/block(+pyramid)/sparse/fused/par/par_unsafe — bit-exact-identical while solving, since values never rise there. `Frontier2DSparseCompact` (finalized values are written out and their blocks freed — nothing left to relax) and the two priority solvers (ascending-order settling breaks under increases; that needs rhs values and a two-key queue, i.e. D\* Lite / LPA\*) declare `resweep: false`. Note the oracle has to approach from the same direction: the update truncates with `>> PROB_BASE_BIT`, so the fixed point is an interval ~1 LSB wide and a descended field differs from an ascended one by 1–2 units out of 3e9 — *visit order*, however, does not matter (design: `docs/superpowers/specs/2026-08-08-vi-solver-observe-design.md`; the 本家 full-sweep solver lives in `solvers::original`). The 7 canonical solvers — `Reference`, `Frontier2D`, `Frontier3D`, `FrontierStack`, `BlockRefine`, `PyramidSweep`, `StreamMimic` — are the set `bench_summary` gates as bit-exact; the other 6 are performance variants (`Frontier2D` Par/ParUnsafe/Fused/Sparse — `std::thread`-parallel — plus the out-of-core `Frontier2DSparseCompact`) and two priority-queue solvers (`PriorityLabelSetting`/`Correcting`), exercised via `bench_map` / `vi_prio_measure` / external `vi_compare` scripts. (The tau/topk/coarse-theta approximation experiments and the SoA/Pad serial variants were removed in the 2026-08 trimming pass; `frontier2d_pad.rs` survives as the shared `Padded` model the parallel solvers build on.) Each solver applies the original per-cell Bellman update over an active set, so the converged value of reachable cells is bit-exact with the ROS1 original (proven by `solvers::conformance`). This is the active CPU model. The value function is 3-D (x, y, θ): a belief-uncertainty dimension b was tried (a 4-D field whose goal gating made the policy detour through informative terrain) and **removed** — the localizer side, windowed or whole-map, turned out to be enough, and the 4-D field cost `belief_levels`× the memory of `states` *and* `sweep_orders` while only three solvers could express its cell-dependent transition. Design: `docs/superpowers/specs/2026-06-08-vi-reference-faithful-port-design.md`, `2026-06-09-vi-u64-fast-solvers-design.md`.
- `vi_lib::bitboard` — the value-type-agnostic `bitboard` primitives (3-D θ-periodic dilation, 2-D AND/OR, enumerate) that `vi_lib`'s frontier solvers reuse and the `vi_bench` `bitboard` microbench exercises. Formerly the standalone `vi_algorithm` crate; folded in during the dependency-trimming pass.
- `vi_bench` — criterion benches + the `bench_summary` / `bench_map` CLIs, all over the u64 `vi_lib` solvers; the `bitboard` microbench exercises `vi_lib::bitboard`.

## Conventions

- C code: `-std=c11 -Wall -Wextra -Werror`. Keep new code warning-clean or the build breaks.
- When changing the HLS data contract (types, tile size, sentinels, transition packing), update **in lockstep**: `vi_fpga/hls/common/vi_hls_common.h` (shared types/sentinels/`cost_of`), the kernel-specific constants in `vi_fpga/hls/tile/src/vi_types.h` / `vi_fpga/hls/stream/src/vi_stream_types.h`, `vi_fpga/driver/uio/vi_bellman_cell.h` (shared per-cell update: host reference + mock + HLS testbench reference), `vi_fpga/host/src/penalty.c`/`transitions.c`, `vi_matlab/.../vi_params.m`, and `vi_bench/src/params.rs` (the u64 model's matching logic lives in `vi_lib`). Then re-run `make -C vi_fpga/host test-host` and `make rs-test`.
- Goal-cell handling: the `PENALTY_GOAL` → 0 substitution when read as a neighbor's penalty is required across all implementations — do not "simplify" it away.
- HW tests are SSH-driven. They assume the target already has the bitstream loaded and the `vi_sweep` overlay applied; they do not program the FPGA themselves.
